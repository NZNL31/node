# node

自用的订阅聚合：把一批公开订阅源拉下来，逐个做**协议级校验**，只留下真正能跑通的节点，
输出一份 `v2.txt` 给 v2rayN（sing-box 内核）用。

公开只是因为放在 GitHub 上方便，不是给人开箱即用的 —— 请当作一份设计记录看。

## 产物

| 文件 | 内容 | 谁写 |
|---|---|---|
| `v2.txt` | base64 分享链接列表。**每个节点都经过真实 HTTP 204 校验**，UDP 协议另做 STUN 校验 | 服务器/CI |
| `v2_hk.txt` | `v2.txt` 的子集：有香港探测点证据的（唯一被验证过与国内可用性相关的信号）| 服务器/CI |
| `v2_asia.txt` | `v2.txt` 的子集：服务器机房在亚洲的 | 服务器/CI |
| `candidates.yaml` | 候选池（拉源 + 解析 + 去重，**未探活**）| CI |
| `geo.json` | 服务器 IP → 归属地/ASN。只用于排序与候选池，**不作为发布门槛** | CI |
| `hk_latency.json` | check-host 香港探测点的延迟缓存 | CI |
| `node_health.json` | 跨轮淘汰状态（连续失败计数）| 服务器/CI |
| `publishable.json` | 上一轮通过 204/STUN 的端点，供探测预算排序 | 服务器/CI |
| `status.json` | 每轮状态快照。想知道「还活着吗」看这个就够 | 服务器/CI |

## 设计取舍

- **CI 供料，服务器定稿。** 「能不能连」取决于从哪台机器测，所以探活与发布只在你能控制的
  那台机器上做；CI 只负责拉源、去重、补香港延迟。
- **只发通过 204 的。** sing-box 的延迟 API 不校验 HTTP 状态码，隧道通 ≠ 出口可用，
  所以每个节点都要真发一次请求拿到 204 才算数。
- **香港探测是唯一有预测力的信号。** 实测同一批节点：美国侧 725/765 通过 204，国内机器
  仅 41/716 可用（5.7%）；只有「仅美国侧通过」的那部分，国内可用率约 0%。带香港标记的
  约 27.3%。所以它同时用于排序和淘汰豁免。
- **地理位置只是先验。** 机房在亚洲的节点国内路由通常更好，但这是相关性、不是验证，
  因此只影响排序和候选池大小。
- **不猜状态码。** 探测失败会保留原因（HTTP 404/503/504），因为 404 说明配置有问题，
  503/504 才是链路问题。

## 脚本

| 文件 | 作用 |
|---|---|
| `fetch_subscriptions.py` | 拉源 → 解析 → 完整性清理 → 去重 |
| `speed_test.py` | sing-box 探活 → 204/STUN 校验 → 跨轮淘汰 → 写产物 |
| `hk_probe.py` | check-host 香港探测点补延迟（只访问一个域名） |
| `geo_lookup.py` | 批量查 IP 归属地，增量更新 `geo.json` |
| `purity.py` / `select_top.py` | 可选：出口 IP 纯净度标注与 top-N 精选 |
| `muse_filter.py` | 从新鲜候选池做 Muse 专用实测：TCP 预筛 + Muse API + 出口国家 |
| `run.sh` | 服务器入口：同步 → 候选池 → 预检 → 探活 → 可选纯净度 → 发布 |
| `doctor.py` | 四层体检：系统时间 / CA / 出网 / 到节点 |
| `check_cn.py` | 任意视角的 TCP 可达率统计 |

## 运行

需要 Python 3.12、一个 `sing-box` 二进制，以及**能正常出网**的环境（探活会被中间设备
拦掉的环境跑不了，`run.sh` 里有预检会直接退出）。

```bash
cp deploy/env.example .env    # 发布方式、并发、可选纯净度、探测视角都在这里
./run.sh
```

自动化在 `.github/workflows/`：`main.yml` 供料、`publish.yml` 发布、`hk.yml` 补香港延迟。
注意 GitHub 的 `schedule` 是 best-effort —— 实测小时级 cron 基本不触发，所以香港探测
并进了 3 小时那个任务。

Muse 的无人值守模式由 `muse.yml` 每 6 小时执行：它使用 GitHub runner 作为探针，
自动更新 `artifacts/muse/latest/`。这是“云端探针 → 节点 → Muse”的结论，不依赖本机；
如果必须保证中国大陆本机可用，仍需在相同网络中运行 `muse_filter.py`。

## 注意

- 自用项目，不保证可用性，也不提供支持。
- 节点全部来自公开订阅源，随时会失效；`v2.txt` 是某一轮的快照。
- 想判断「我这边到底能用哪些」，只能在本地实测 —— 这正是上面「服务器定稿」的原因。
- 给 Muse 选节点时先跑 `python muse_filter.py`。纯净度和香港延迟只能预测可用性，
  不能代替本机的代理握手和 Muse API 请求；脚本默认从较新的 `candidates.yaml`
  里选，把真正通过的节点写到 `v2_muse_ok.txt`，再用这份池子做纯净度排名。
  也可用 `MUSE_SOURCES=v2.txt` 只测已发布池。固定某个地区可用
  `MUSE_COUNTRIES=US python muse_filter.py`。香港探针 400ms 不能直接拿来卡本机
  Muse 往返，后者还包含本机出境、握手和后端响应；默认只记录并按本机耗时排序，
  需要硬门槛时再设置 `MUSE_MAX_LATENCY_MS=1200`。
